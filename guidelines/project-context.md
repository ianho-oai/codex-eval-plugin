# Project context

**When to read:** Before changing the evaluation contract.
**When to update:** When behavior, assumptions, or verified limitations change.

## Contract

Customer discovery combines interview, opt-in local history, and selected repository/PR/MR evidence. The single skill designs customer-specific tasks; the CLI freezes, validates, approves, executes, grades, normalizes, resumes, and displays them. No AI is used to construct dashboards or to decide scores after approval.

Host-side task quality follows an adaptive design, challenge, observe, diagnose, and repair loop. Choose counterexamples from each customer's contract and challenge both false acceptance and false rejection before paid runs; known examples are not exhaustive. Keep observing first and ongoing results with `progress` and `reflect`, including unfamiliar anomalies below automatic thresholds. Diagnose setup, grader/contract defects, scope, or genuine coding failures; never change sealed grades. Agree a bounded repair policy with the customer. Repairs require a new validated revision, approval covering the concrete changed inputs, and fair reruns of all affected lanes; reuse prior explicit authorization only within its scope. Preserve old evidence and costs; cap corrective revisions at two per task. `review-clear` only clears a drained review-owned pause and records the reviewer decision; it never starts work or clears user cancellations.

Compare selected native Codex and Claude Code agents using API-key authentication, with optional GitHub Copilot using explicit account/token authentication. Their built-in prompts and tool implementations differ; this is a product-and-model comparison, not a controlled model-only experiment. Deterministic orchestration does not imply deterministic inference. Use repeated trials and retain every scheduled cell.

GitHub Copilot CLI is an opt-in experimental third provider for local execution. Require an explicit `COPILOT_GITHUB_TOKEN` or a frozen `execution.copilot_account` selecting the active native github.com login, a pinned executable/version, and a sealed per-attempt `copilot_max_ai_credits` setting (null for no limit; otherwise minimum 30). Native-login mode preserves the OS home for credential lookup but creates a fresh Copilot configuration with only the selected identity and no inherited hooks/settings; environment tokens are ignored. Token mode isolates both homes. Never silently inherit accounts or use BYOK as an access-policy workaround. Native token events and AI billing units remain separate from USD; never price Copilot using the direct-API rate card. Doctor cannot verify its account model listing. Access-denied attempts are infrastructure-invalid. Native usage JSON and metadata-only OTel are retained alongside events. New runs ingest native tokens and top-level credits plus a separate dollar usage valuation; net currency cost remains null. Customer configure/smoke commands accept explicit native account selection, verified CLI path/version, effort and optional credit limits; new selections have no credit cap, and existing settings are preserved. Stable CLI 1.0.88 and low-effort Astra/Sol editing/grading were verified on 2026-09-23. Unknown normalized fields stay null. See the packaged [Copilot reference](../plugins/codex-eval-plugin/skills/evaluate/references/copilot.md).

Default execution is local, using self-contained trusted task fixtures, clean candidate directories, a separate verifier process, and existing lightweight test runners. Do not add Docker, platform SDKs/simulators, SwiftUI/UIKit UI tests, desktop integrations, browser downloads, or external services during ordinary discovery/task design. For native-app workflows, extract representative logic and disclose the narrower coverage and any language adaptation. Difficulty comes from behavior and interacting modules. Local execution cannot enforce held-out-test secrecy or host isolation; do not label it hermetic. Docker remains an explicitly requested advanced option, with pinned images and separate verifier containers.

Scores are binary. Comparison views exclude explicit rate-limit error trials for every provider and retain their counts separately. Successful retries contribute non-rate-limit task metrics; raw signed evidence and full spend accounting remain unchanged. Rate-limit-only cells remain unmeasured. Infrastructure errors and interrupted attempts score zero in the all-attempt summary but are separately categorized. Scorable success rates exclude infrastructure-invalid rows and always display their count. Missing usage is null. With an explicit spend stop, unknown spend unrelated to authorized rate-limit retries pauses execution because the threshold cannot be enforced from missing telemetry. By default no spend stop is configured, and missing telemetry is retained without stopping dispatch.

The spend threshold is checked before queue dispatch. In-flight calls can overshoot it; provider-side limits remain necessary for a hard billing cap. No automatic provider fallback or silent model substitution. Explicit native rate-limit, capacity, connection and temporary service failures have bounded automatic retries and a shared provider cooldown; other failures do not.

Model IDs, pricing, and CLI compatibility in the bundled catalog are versioned snapshots; verify account access and configuration support before use. Access from one terminal does not establish access from another host or agent session. See [the validation guide](../VALIDATION.md) for offline and live-provider checks.

Validate native editing in the intended launch context when support is uncertain. Nested agent sandboxes can fail even when the same CLI works in a normal terminal. Keep native sandbox settings intact; use an authorized ordinary terminal handoff when necessary, record the boundary, and preserve contaminated attempts separately from fresh comparison runs. An outer exit code or agent summary is insufficient proof of successful native editing.

New customer suites use schema 3 with two tiers: Basic spans the former easy/medium/hard range; Hard targets former harder-1/harder-2 style repository engineering. Default to three Basic and five distinct Hard tasks per workflow: investigation/repair, feature integration, and state/recovery/compatibility, adapted to customer evidence. The CLI seeds eight slots and enforces the three/five counts; qualitative task review establishes substantive interactions and distinctness. A customer-requested workflow `difficulties` subset instead seeds/requires one task per selected tier. Do not infer a reduced scope. Keep the reference collection (1,658 metadata records and 46 design cards) and source provenance; benchmark inspiration does not certify equivalent difficulty. Schema 1/2 and existing run-local harder labels retain their historical meanings and evidence. New portfolio generation refuses legacy suite targets rather than silently upgrading them. Initialized harness examples are all Basic and must be replaced with customer tasks; explicit smoke suites remain exempt from portfolio coverage.

The skill is explicit-only: `skills/evaluate/agents/openai.yaml` disables implicit invocation, and its entrypoint requires a user request for Codex-versus-other-agent evaluation tests. General coding/testing and plugin maintenance do not trigger it. Local history skips recognized automatic approval-review transcripts and reports truncation and parser completeness separately; none of these counters proves exhaustive semantic workflow review.

The dashboard is chart-first: “Workflow evaluation,” identical stable X-axis/Y-axis selectors for average score, cost per verified success, task cost, latency, and token metrics on a separate row, grouped model checkboxes, task checkboxes grouped by difficulty, provider-colored points when any repeat passes and grey points when none pass, without an outcome filter, toggleable model-name point labels without connectors, and hover/focus popups with task outcomes or grouped coverage and selected-axis values. A task summary table lists descriptions, difficulty, and development type; model summary tables, summary cards, combined-run badges, are omitted; compact metric definitions appear as bullets below the chart. New runs snapshot task descriptions; older runs use matching local definitions when available. Detailed telemetry/provenance remains in reports and exports. Codex is blue300 (#339cff) from the OpenAI developer palette; Claude is orange and Copilot purple.


New runs default to one iteration per task/model/effort (including smoke). Only after the entire approved first-round matrix across all selected harnesses and Basic/Hard tasks is complete and reviewed, ask permission for exactly two additional attempts per configuration; no automatic extra paid repeats. Resolve missing/blocked coverage or obtain an explicit scope reduction before offering the follow-up. Compute any pooled three-observation mean and median from the raw observations, retaining source identities and pass counts. Follow the skill's staged-repeat reference for separate sealed follow-up runs and explicit pooled-report provenance. Chart points are arithmetic means within a run/task/provider/model/effort; failures remain included, missing values remain null, and mixed/partial outcomes disclose pass/repeat counts. Task averages never combine separate runs or effort configurations; grouped model summaries are a distinct descriptive view, not a pooled three-observation report. Task tables use authored `human_summary` text, with a concise metadata fallback for older runs. Select-all toggles operate globally and by difficulty/provider.

`configure` selects models, task IDs, and repeats before validation/approval; optional suite `selection.task_ids` narrows execution while keeping the complete designed portfolio. `dashboard --scope` stays within the supplied evaluation directory or run, combining all selected providers there. Default unscoped dashboards still discover all live evaluation runs.

Axis dropdown options stay fixed across providers. New views default to task cost versus latency, and saved or user-selected axes never change automatically based on provider data. Each axis has an independent logarithmic toggle. Nonpositive measurements are explicitly counted as unplottable on log axes; values are never shifted or silently changed. Provider checkbox groups use the same blue/orange palette as successful points.

Post-run difficulty relabeling uses a run-local `difficulty-labels.json` receipt tied to the original run seal, with a requester, reason, and exact task/from/to mappings. Reports, CSV, and dashboards apply these labels after verifying original evidence and retain `recorded_difficulty`. `harder`, `harder-1`, and `harder-2` are supported as display categories after `hard`; authored task schemas and sealed run inputs retain their original difficulty tiers. Relabeling never rewrites scores or sealed artifacts.

The run CLI defaults to a five-worker queue with immediate refill. `--workers 1` restores sequential execution; shared `--slot-pool` directories enforce a combined limit across batches. Scheduler metadata records workers, implementation hash and concurrency caveat. A single coordinator writes checkpoints; stop requests, unknown spend and budget thresholds drain active work before stopping.

New suites expand every selected model across its catalog-supported efforts. `configure --all-efforts` expands existing suites; repeated `--effort` narrows to levels supported by every selected model. Customer plans disclose capability exclusions, and model labels include effort. The first sweep uses one repeat; extra rounds require later customer approval.

### Default model sweep and spend policy

New suites, smoke tests and readiness probes default to no agent or grader timeout (`limits.agent_seconds: null`, `limits.grader_seconds: null`), disclosed in preflight. Customers may explicitly choose numeric limits before approval; numeric readiness limits remain capped at 120/30 seconds. Existing approved and in-flight runs retain their frozen limits. Timeout changes require a fresh approved revision and output directory; never rewrite historical evidence.

New evaluations default to all cataloged GPT-5.6 models and GPT-6 Astra, plus cataloged default Claude models, across every supported single-agent effort level. Preflight lists the exact matrix and repeats, announces **no spend stop**, and tells the customer to specify otherwise before approval. Limited-access models are included; unavailable lanes remain visible.

`configure SUITE --all-models --all-efforts --repeats 1 --no-spend-stop` restores these defaults. Select alternatives with repeated `--model PROVIDER:MODEL` / `--effort LEVEL` flags. Set an optional stop with `--spend-stop-usd AMOUNT`. A null `limits.spend_stop_usd` disables both the scheduler spend stop and Claude's native budget flag; missing costs remain null and do not stop dispatch in this mode. Time limits, turn limits, bounded rate-limit retries, and explicit pause requests still apply. Existing approved suites retain their frozen settings.

Evaluation tasks should be feasible with the supplied context, with verified correctness, cost, latency, and token use reported together. Do not simplify Hard tasks to target a high pass rate. Keep requirements explicit, provide enough context, and allow reasonable execution time. Difficulty increases coding work within a simple prepared environment; provisioning is outside the timed task. Expected success is a design target, while actual pass/fail remains determined by the same fixed checks for every model.

The customer entry point is `CUSTOMER_STARTER_PROMPT.md`: installation followed by a copy-ready Codex kickoff prompt. README and OVERVIEW route there; detailed operator commands are in `docs/CLI_REFERENCE.md`. Doctor validates known per-model CLI minimums and marks account access as unprobed. The bundled catalog records per-model minimum CLI versions, which preflight enforces. Updating CLI pins requires fresh validated/approved inputs; historical frozen runs are preserved.

Mythos is excluded from default selections. The evaluation skill runs authenticated `doctor --check-model-access` before final approval, verifies upgraded executable paths, and asks the customer to upgrade when required. User-requested setup-error resets/model exclusions are view receipts with preserved original evidence; replacements use newly approved suites.

Model median diamonds summarize currently selected task/configuration averages with equal weight per plotted average. Median focus offers Model × effort (default, grouping by provider/model/effort) and Model (pooling efforts within each provider/model). Providers never share a median. Grouping applies to medians, score denominators, pies, thresholds, tooltips and labels, and persists in the URL. Muting a model median is independent of muting its effort medians. Compute paired X/Y medians in raw units before log clipping. The top-right Median focus switch fades task points/labels and enlarges medians; it does not alter inputs or saved results.

The average-score option on either axis forces median mode, including with one selected task, and plots only aggregated model/effort diamonds. The score axis is successful completed runs divided by all completed runs, expressed as a percentage on a fixed linear 0–100% scale; it is not the median of binary grades. Include completed results with missing other-axis telemetry in the score and exclude pending runs. The other metric remains the median of measured task/configuration averages. Unknown scores stay unplotted; zero scores remain visible. The saved URL restores this mode, and switching both axes away from aggregate outcome metrics unlocks Median focus; each score axis disables its own log scale.

The circle above each median is a proportional pie: green is successful completed runs divided by all completed runs for the selected model/effort group; red is the remainder. Include selected results with missing axis telemetry in that fraction. Pending repeats are excluded from the pie denominator and disclosed in hover/focus details alongside the exact passed/recorded fraction. The Show score pies checkbox in Median focus defaults on and hides only the pies and their legend; its setting is saved in the URL view without changing medians, scoring, or hover details.

Host-side evaluation progress uses installed visualize/live skills when available in Codex desktop, with one apply_patch-refreshed fragment and read-only `progress RUN_DIR ...` snapshots. Keep visualization outside the sealed headless agents and preserve the single exported evaluation skill. Missing visualization support falls back to text; saved running state is not proof of process liveness.

For ordinary axes, median controls require at least two selected tasks, and diamonds/legend appear only in Median focus. With zero or one selected task, ordinary points retain normal contrast; selecting multiple tasks restores the prior focus preference. Either aggregate outcome axis forces grouped mode even for one task. Labels follow the selected model or model × effort grouping.

Clicking a median diamond toggles that model/effort diamond, label, and result pie to grey; clicking again restores them. Enter/Space on the diamond provides the same toggle. This display state survives live refreshes, filters, and axis changes without changing any data or calculations. The URL's versioned `view` parameter stores task/model omissions, axis metrics/scales, label and median toggles, minimum pass rate, and muted medians. Reloads and copied links restore these settings; invalid fields fall back to defaults. Newly discovered tasks/models stay included unless explicitly omitted, and CSV export remains the full server dataset.

Median focus includes a 0–100% minimum pass-rate slider. It filters entire model/effort medians using passed divided by completed runs for selected tasks, including recorded infrastructure errors in the denominator and excluding pending runs. Apply the threshold after aggregation; never discard failed rows before computing medians. Default zero shows all medians, and the control is hidden outside Median focus. Task points and saved evidence are unaffected.

Customer runs gate dispatch on a small native edit-and-test probe per provider in the actual launch context, with separate receipts and costs included in spend checks. Discovery proposals include the CLI-generated coverage receipt and customer-confirmed scope; selected samples and exports never imply a complete lookback crawl. Both dashboard log axes default on. ### Select evaluation harnesses

Use `configure SUITE --provider codex --provider copilot --all-efforts` for the catalog defaults of those harnesses; add `--provider claude` for all three. Repeated provider flags replace the selection and cannot combine with exact `--model` flags. Copilot defaults are Astra, Sol and Terra; other catalog models remain available through `--model`. Bare `--all-models` restores Codex + Claude defaults. Configure only the selected providers’ credentials, verify their installed executables, then validate and approve the exact matrix. Copilot model access still requires its separate documented smoke checks.

The Task cost dropdown option displays native Copilot dollar usage valuation alongside other providers’ USD cost metrics through a display-only projection. The tooltip and chart note identify Copilot usage valuation as distinct from invoice cost. Copilot-specific credit/value options are removed from both identical axis dropdowns; old saved axis selections migrate to Task cost. The display projection does not modify native Copilot billing fields, signed results, accounting or CSV. Codex dashboard repricing is a separate projection described below.

Codex dashboard costs are recalculated from recorded tokens using the packaged `ceval/data/rates.json` on every request (15-second browser refresh). Apply this after integrity checks, cache-write recovery and comparison exclusions, before averaging. Dashboard JSON/CSV carry the current estimate, original recorded cost, and pricing path/hash. Claude native reported cost and Copilot usage valuation remain untouched. Original signed evidence, frozen run pricing, spend accounting, and static reports retain their existing behavior. Missing rates or required telemetry never fall back to old dollar totals. Synthetic demo costs are not repriced.

Cost per verified success on either axis forces grouped Median focus. Compute sum of completed-run costs, including failures, divided by verified passes for the selected provider/model[/effort] group. Recover total cost from each repeat average times its recorded repeat count; never take medians or averages of ratios. Include rows missing other-axis telemetry in the ratio, exclude pending runs, and show unavailable for zero passes or any missing completed-run cost. This uses the same provider-specific cost basis as Task cost; it is an observed ratio, not a predicted retry cost. Score and this ratio remain aggregate metrics, while ordinary metrics retain median aggregation.

# Evaluation progress in Codex

Use this during execution in the host customer conversation. It supplements the fixed results dashboard and never changes the tested agents, frozen suite, concurrency, approvals, or provider calls. Use the installed visualize skills, not a developer-specific filesystem path. Preserve the plugin's single evaluation skill.

1. Launch the approved runner once with a nonblocking tool invocation. Retain its session handle; do not relaunch it to refresh progress. As soon as its first checkpoint exists, run `EVAL progress RUN_DIR`. Before that, show “Awaiting start” with an unknown denominator, or use the approved plan's exact count explicitly labeled as planned.
2. Read `visualize:visualize` and, when available in the supported desktop app, `visualize:live`. Prefer live mode for ongoing runs. Create one small progress fragment in the thread's writable visualization directory or an ignored customer evaluation directory. Use literal markup with real counts. Register the live reference once in commentary according to that skill's contract.
3. Use a compact completed/remaining bar, active-at-checkpoint count, and passed/failed/error counts. For multiple explicitly selected runs, call `EVAL progress RUN_A RUN_B ...` and show up to three run lanes; aggregate further runs rather than making a long sidebar. Show the saved checkpoint timestamp. A finished attempt is not necessarily a pass; remaining includes active work. Active slots may include rate-limit backoff. Null counts stay unavailable; do not invent zero, ETA, task names, or a retry state.
4. While execution continues, poll the same runner session with bounded waits and sample progress about every 15–30 seconds or after a meaningful completion/blocker. Update the same registered fragment with one `apply_patch` call when values change; shell writes do not refresh the live surface. Never fetch localhost, use WebSockets, or call provider APIs from the fragment. Do not re-emit live references or accumulate progress cards. Keep the command output as the source of truth and treat supplied names as text, never executable markup.
5. If only inline visualize is available, use milestone snapshots under its output contract and normal text progress between them; do not claim automatic refresh. If neither skill is available, continue with the CLI output and concise text updates. No install is required.
6. Read one final checkpoint after the runner exits. Update the same live view to the saved complete/stopped state and retain genuine failures. An old checkpoint marked running is not proof that its process is alive; verify the session or label it as last recorded state. If the turn ends before the run does, keep the latest checkpoint timestamp visible and do not promise background updates. Keep final results in `EVAL report` and the existing dashboard.

`progress` reads only the supplied run directories; it does not scan customer histories, read provider event bodies, modify runs, or make network calls. It reports the original schedule and saved outcomes, including historical results hidden by explicit dashboard view receipts. If the manifest/results checkpoint counts differ while the writer advances, outcome counts are temporarily null; refresh on the next observation. A read error can occur during a checkpoint/retry transition: retain the last snapshot with its timestamp and retry observation on the next interval. Persistent errors should be reflected in the view rather than replaced with success. Observation errors never authorize restarting or changing the paid runner.

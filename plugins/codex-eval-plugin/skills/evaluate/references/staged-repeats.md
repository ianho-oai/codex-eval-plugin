# First round, then optional consistency rounds

Default to one iteration for every selected task × provider/model × supported effort. Preserve narrower user selections and any explicitly requested repeat count. The approved model/effort matrix still applies to every selected harness, including opt-in Copilot; one iteration reduces initial spend, not coverage. Bounded retries for transient provider/connection problems remain part of an iteration, not extra consistency rounds. Never retry a genuine coding failure to turn the first observation into a success.

Complete the entire approved first-round matrix before offering consistency rounds: every selected Basic and Hard task, model, and effort gets one scheduled iteration. Do not start repeat two for an early-finishing configuration while other first iterations remain queued or running. Check every first-round run if providers or tasks were split across directories: no queued or active cells may remain, and recorded outcomes must reconcile with the approved schedule. A blocked or unavailable combination is unresolved coverage, not completion; resolve it or obtain an explicit scope reduction before offering the follow-up. Genuine failures count as the first iteration and remain visible.

After completing and reviewing the first round:

1. Present pass/fail, latency, token usage, known spend, missing costs, and remaining coverage. One sample cannot measure run-to-run consistency.
2. Offer **two additional iterations per configuration**, giving three observations total. Show the exact additional attempt count and a rough incremental cost estimate from first-round measured costs (roughly twice the full accounting costs, including excluded rate-limit trials, for unchanged coverage). Explain missing telemetry, retries, and variable output/cache use; this is not a price guarantee. Offer a narrower matrix if the customer prefers.
3. Wait for explicit approval before any additional paid consistency runs. Declining or not responding means the completed first-round evaluation is the deliverable. Initial run approval and no spend stop do not authorize extra rounds. Repairs and provider retries use their separate agreed policies.
4. For approval covering the extra rounds, preserve the first run and prepare a separate customer-owned follow-up suite with identical tasks, graders, model/effort settings, CLI pins, pricing, environment, and concurrency, but `--repeats 2`. Validate and seal it, record approval, then execute into a fresh run directory. Do not change the old suite to three and resume it: repeats affect the seal, and a fresh three-repeat run would buy three additional iterations. Record which first-round run the follow-up extends. If other inputs changed, report it as a new comparison instead of pooling it.
5. Run the normal progress, reflection, report, and scoped dashboard flow. Include all configurations in the approved follow-up, not just failures or favorable models. Preserve failed attempts and missing telemetry.

The current dashboard averages within each run and does not automatically pool the first round with the two-repeat follow-up. Disclose this. After an approved follow-up, produce a separately labeled three-observation summary only after verifying matching inputs above and retaining source run/attempt IDs. For each task/provider/model/effort, verify exactly one first-round observation plus two follow-up observations. Calculate the mean and median from the three raw values: mean `(a + b + c) / 3`, median the middle sorted value. Never average two run means or two run medians; an equivalent mean is `(first + 2 * follow_up_mean) / 3` when complete. Report verified passes out of three separately rather than using the median binary grade as the success rate. Do not merge efforts or changed task revisions. Missing measurements keep that metric unavailable; show observed/expected counts and pass counts, and retain every original result. Three observations improve visibility into variability but are not statistical proof of reliability.
